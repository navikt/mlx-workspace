## The three failures, and why the failure rate is not a result

Corrected after a second review read the session logs and the server log. The
first account, that qwen3.8 failed two of five runs, is not what happened.

**Runs 07 and 09 were killed by this harness.** The model's plan phase did fail
on its own terms: it fetched the 91 KB Met.no payload, then spent 27 and 25
turns inspecting that file one key at a time and never wrote a plan. It hit one
403, deliberately, with a browser User-Agent, and diagnosed it correctly. This
is non-convergence, not the `example.com` loop that killed run 05 of the
previous round.

What turned a 15-minute planning failure into an 85-minute empty run is mine.
The 900s cap fired, `adba4f5` pkilled the client mid-prefill, and the server
went down with it:

    01:37:33  Prompt processing progress: 12288/16209
              BrokenPipeError: [Errno 32] Broken pipe
              RuntimeError: [METAL] Command buffer execution failed:
                            Insufficient Memory

The generation thread died and the HTTP listener stayed up, so the implement
turn waited out its full 4200s cap against a server that could not answer.
`restart_server()` runs once per run, before the plan phase, never after a kill.
Byte-for-byte the same sequence at 03:12:35 for run 09.

**Run 10 was a path typo the harness scored as success.** The model asked to
read `.../qwen3.6-35B-A3B-OptiQ-4bit/Weather-CLI/WEATHER_CLI_SPEC.md`, taking
the casing from the HF repo id that opencode puts in its system prompt. opencode
compares paths as strings, treated it as outside the workspace, and auto-rejected
it. The rejection ends the session rather than returning an error the model could
recover from, and the wrapper printed `✓ exit 0`. The same model has produced
20+ path rejections of this shape in earlier logs.

So the honest reading is that all three failures are real failure *modes* and
none of them is a measured failure *rate*. 2 of 5 against 1 of 5 is Fisher
p=1.0; separating 40% from 20% would need roughly 80 runs an arm. Publishing
2/5 against 1/5 would publish the harness.

## What this round cannot say

The arms are not configured alike. `MLX_OPENCODE_CONTEXT` is 131072 for
qwen3.8 and 65536 for qwen3.6, so qwen3.6 compacts mid-run and works from a
summary of the spec while qwen3.8 never approaches its threshold; `reasoning_effort`
is set on qwen3.8 only. This was accepted deliberately before the round on the
grounds that each profile is measured as it ships, which makes these absolute
readings per arm and not a comparison. Any sentence of the form "qwen3.8 beats
qwen3.6" is not supported by this round.

Three runs an arm meets the bar for scoring and not the five-run bar for
publishing.
