# Local models for Copilot overage: status, 27 August 2026

## Where we are

We have been testing whether local language models running on developer laptops can absorb some
of the GitHub Copilot premium request usage that pushes our heaviest users into their $400
monthly cap.

Two models now run a full coding task on standard Nav hardware. These are measured, not
estimated:

| Model | Memory footprint | Time on the benchmark task | Code quality |
|---|---|---|---|
| Qwen3.8-27B 4-bit | 17.9 GB | 32m 21s | 8.5/10 |
| Qwen3.6-35B-A3B | 23.3 GB | 6m 45s | 6.8/10 |

Both fit the 32-48 GB range our developers run, at about half the available memory. Memory was
never the limit. Speed and code quality are, and they pull in opposite directions. The faster
model writes weaker code.

## What changed in our thinking

We started by asking whether local models could replace a Copilot seat. They cannot. On the
benchmark task they are ten to forty times slower, and nobody will wait six minutes for something
they currently get in seconds.

Reading the invoice changed the question. Our spend is premium request overage against a hard
cap, not seat price. So the problem is not cost per request. The problem is what happens to a
developer who exhausts their allowance on the 20th and loses access for the rest of the month.

Against that, a local model is not competing with Copilot. It competes with having no assistant,
and six minutes reads differently in that light.

That points somewhere sharper. Rather than moving heavy users to local models wholesale, route
the cheap requests locally and keep the premium allowance for work that needs a frontier model.
Renaming a symbol, drafting a commit message and writing a test stub each cost the same allowance
as a hard architectural question. Splitting them extends the cap without slowing anyone down on
the difficult work.

## An unrelated finding worth flagging

While building the test harness we found that the models we were evaluating could read one
another's work and write to the host machine. One listed every other model's finished solution.
Another invented a command line tool that does not exist, then tried to install it system-wide
and changed local package manager state in the process.

Neither did any damage. Nothing stopped them either. Test runs now execute inside a kernel-level
sandbox confined to their own directory. Anyone else running agentic tools locally should know
this: by default an agent has the same access as the developer running it.

## What we do not know yet

We have not started a rollout, for one reason. Every measurement we have comes from building a
complete application from scratch. That is the hardest task shape, and the one we would never
send to a local model. The use case we settled on is cheap, routine operations, and we have not
measured a single one.

The evidence is also thinner than the table above suggests. Each result is one run. The speed gap
between the two models is far too large to be noise. The code quality difference is not, and we
would not rank them on it yet. Every benchmark so far has been a JavaScript task, while our
developers work on Kotlin services.

## Next steps

1. Measure the real use case. Routine operations against an actual Kotlin service, this week.
2. Repeat the fastest model's benchmark three times with corrected settings, replacing a single
   sample with a real measurement.
3. Pull the distribution of premium request types for our heaviest users. If most of their usage
   is routine work, local models solve a large part of the problem. If it is mostly hard agentic
   work, they solve very little. We should know which before building anything.

If those come back well, a hand-held alpha with a few volunteers is weeks away. If they do not,
we will say so.
