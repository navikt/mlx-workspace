# Local models for Copilot overage: status, 27 August 2026

## Where we are

We have been testing whether local language models running on developer laptops can absorb some
of the GitHub Copilot premium request usage that is pushing our heaviest users into their $400
monthly cap.

Two models now run a full coding task on standard Nav hardware, measured rather than estimated:

| Model | Memory footprint | Time on the benchmark task | Code quality |
|---|---|---|---|
| Qwen3.8-27B 4-bit | 17.9 GB | 32m 21s | 8.5/10 |
| Qwen3.6-35B-A3B | 23.3 GB | 6m 45s | 6.8/10 |

Both fit comfortably within the 32-48 GB range our developers run, with room to spare. Memory was
never the limiting factor. Speed and code quality are, and they pull in opposite directions: the
faster model writes noticeably weaker code.

## What changed in our thinking

We started out asking whether local models could replace a Copilot seat. They cannot. On the
benchmark task they are between ten and forty times slower than Copilot, and nobody is going to
wait six minutes for something they currently get in seconds.

Understanding the invoice changed the question. Our spend is premium request overage against a
hard cap, not seat price. That means the problem to solve is not cost per request, it is what
happens to a developer who exhausts their allowance on the 20th of the month and loses access
entirely for the rest of it.

Against that, a local model is not competing with Copilot. It is competing with having no
assistant at all, and six minutes is a very different proposition in that light.

This led to a sharper idea. Rather than moving heavy users to local models wholesale, route the
cheap requests locally and preserve the premium allowance for work that genuinely needs a
frontier model. Renaming a symbol, drafting a commit message and writing a test stub each consume
the same allowance as a hard architectural question. Separating those extends the cap without
costing anyone their productivity on the difficult work.

## An unrelated finding worth flagging

While building the test harness we found that the models we were evaluating could read one
another's work and write to the host machine. One listed every other model's finished solution.
Another invented a command line tool that does not exist and attempted to install it system-wide,
modifying local package manager state in the process.

Neither caused harm, but neither was prevented by anything. Test runs now execute inside a
kernel-level sandbox confined to their own directory. This is worth knowing for anyone else
running agentic tools locally: the default posture gives an agent the same access as the developer
running it.

## What we do not know yet

We have deliberately not started a rollout, for one specific reason. Every measurement we have
comes from building a complete application from scratch, which is the hardest task shape and
exactly the kind of work we would never send to a local model. The use case we have landed on is
cheap, routine operations, and we have not yet measured a single one.

We also want to be straight about the strength of the evidence. Each result is a single run. The
gap in speed between the two models is far too large to be noise, but the difference in code
quality is not, and we would not rank them on it yet. Every benchmark so far has been on a
JavaScript task, while our developers work on Kotlin services.

## Next steps

1. Measure the actual use case: routine operations against a real Kotlin service, this week.
2. Repeat the fastest model's benchmark three times with corrected settings, to replace a single
   sample with a real measurement.
3. Pull the distribution of premium request types for our heaviest users. If most of their usage
   is routine work, local models solve a large part of the problem. If it is mostly hard agentic
   work, they solve very little, and we should know which before building anything.

If those come back well, a hand-held alpha with a small number of volunteers is a matter of
weeks, not months. If they do not, we will say so.
