# Local models for Copilot overage: status, 27 August 2026

> Superseded by the 29 August data. The alpha ships one model, not two. See
> [`alpha-model-decision.md`](alpha-model-decision.md). The numbers below are left as they were
> recorded on 27 August.

## Where we are

We are testing whether local models on developer laptops can absorb some of the GitHub Copilot
premium request usage that pushes our heaviest users into their $400 monthly cap. Two now run a
full coding task on standard Nav hardware. Measured, not estimated:

| Model | Memory footprint | Time on the benchmark task | Code quality |
|---|---|---|---|
| Qwen3.8-27B 4-bit | 17.9 GB | 32m 21s | 8.5/10 |
| Qwen3.6-35B-A3B | 23.3 GB | 6m 45s | 6.8/10 |

Both fit the 32-48 GB our developers run, at about half the available memory. Memory was never the
limit. Speed and code quality are, and they pull against each other.

## What changed in our thinking

Local models cannot replace a Copilot seat. They are ten to forty times slower on the benchmark
task, and nobody waits six minutes for what they get in seconds today. But our spend is premium
request overage against a hard cap, not seat price, so the real problem is the developer who
exhausts the allowance on the 20th and loses access for the rest of the month. In that gap a local
model competes with having no assistant at all, and six minutes reads differently.

So the plan is routing, not replacement. Renaming a symbol, drafting a commit message and writing a
test stub each cost the same allowance as a hard architectural question. Send those to a local
model, keep the premium allowance for work that needs a frontier one, and the cap stretches without
slowing anyone down on the difficult work.

## An unrelated finding worth flagging

While building the test harness we found the models under evaluation could read one another's work
and write to the host machine. One listed every other model's finished solution. Another invented a
command line tool that does not exist, tried to install it system-wide, and changed local package
manager state doing it. Neither did damage, and nothing stopped them either. Test runs now execute
inside a kernel-level sandbox confined to their own directory. By default an agent has the same
access as the developer running it, which anyone running agentic tools locally should know.

## What we do not know yet

No rollout has started, for one reason. Every measurement comes from building a complete
application from scratch, the hardest task shape and the one we would never send to a local model.
The use case we settled on is cheap, routine operations, and we have not measured a single one.

The evidence is also thinner than the table suggests. Each result is one run. The speed gap between
the two models is far too large to be noise. The code quality difference is not, and we would not
rank them on it yet. Every benchmark so far has been a JavaScript task, while our developers work
on Kotlin services.

## Next steps

1. Routine operations against an actual Kotlin service, this week. That is the real use case.
2. Repeat the fastest model's benchmark three times with corrected settings, replacing a single
   sample with a real measurement.
3. Pull the distribution of premium request types for our heaviest users. Mostly routine work and
   local models solve a large part of the problem. Mostly hard agentic work and they solve very
   little. We should know which before building anything.

If those come back well, a hand-held alpha with a few volunteers is weeks away. If they do not, we
will say so. Full data, including every failed run and correction, is in `MODELS.md`. Longer
write-ups are in `reports/`.
